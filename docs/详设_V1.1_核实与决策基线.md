## 一、冻结的四个架构决策（已确认，无保留意见）

1. **只保留一套剧情计划数据**：`StoryPlan` 为唯一计划模型；`outline.json` 若保留只能是 StoryPlan 的导出投影，禁止双份独立维护。
2. **先回填存量正文，再启用记忆检索**：两级初始化（低成本映射 + 按需深度提取），初始化幂等可重入。
3. **补齐版本机制**：`Chapter.Revision`（单章内容版本）+ `memory/meta.json` 的 `memory_revision`（正式记忆快照版本，一次提交递增一次）。
4. **统一实体 ID 与提交协议**：记忆系统复用 knowledge 的实体 ID（`c_xxx`/`w_xxx`），禁止另建；提交走带日志的可恢复协议。

P1–P18 全部采纳，处理结论见修订方案原表；P5 的 409 只是首期保护、不替代写入串行化；P15 偏移单位=rune、强制绑定章节 revision。

## 二、源码核实事项 1：调用关系与锁粒度（✅ 已核实，附证据）

**锁模型**：`store.Store` 持单一 `mu sync.Mutex`（store.go L56–59），全部公共方法（Load/Save/Commit/Finish/Fail/Import…）各自**全程持锁**——锁粒度=单操作，**跨操作的组合不是原子的**。

**分析器模式**（analysis/manager.go L103–219）：锁外调 LLM → 锁内 `CommitAnalysis(revision, …)` → revision 不匹配返回 `ok=false` → Manager 重入 `step()` 自愈。**结论**：修订方案"共享写入锁 + 锁内二次校验"与现有结构天然兼容——`store.mu` 就是那把共享锁，无需新建锁机制（见 Q1 简化建议）。

**`merge.matchCharacter` 现状**：是 analysis 包**私有函数**（merge.go L180–189），仅被 `applyChapter` 调用；且 novel 包另有第二套归并逻辑 `normalizeKey + mergeCharacter`（project.go L210–219、L294–311）——**两套行为不一致**：analysis 版做"名字+别名 key 集合相交"匹配，novel 版只在 `Normalize()` 时按主名精确 key 合并、不做别名交叉。**结论**：修订方案"复用 matchCharacter"成立，但须先把它提升到共享包（建议 novel），并统一两套归并行为，否则 Entity Registry 会继承行为分叉。

**`CommitAnalysis`/`FinishAnalysis` 现状**（store.go L375–435）：revision 匹配时**无条件写** knowledge.json + project.json（相同内容也重写）。**结论**：修订方案 5.2"仅实际写入正式记忆才递增 memory_revision"的判断点正确且必要；同时确认 knowledge.json 更新**不等于**记忆版本变化（两套数据已分离，方案第九章原则与代码现状吻合）。

**`SaveChapter` 现状**（store.go L226–272）：每次保存无条件 `project.Revision++` + 置 `Analysis` 回退到该章前并 pending 重析；**无"内容相同则不动"的逻辑**，`Chapter` 目前无 Revision 字段。**结论**：修订方案 5.1 规则（内容变化才递增）为新增实现；建议顺带"内容未变时跳过重析置位"，避免无谓重析。

## 三、源码核实事项 2：写入顺序与原子性边界（✅ 已核实，附证据）

**单文件原子性 ✓**：`writeJSONFile` = temp → write → Sync → Close → Rename（store.go L627–658）；Windows 上 Go 的 `os.Rename` 走 MoveFileEx(REPLACE_EXISTING)，原子。

**跨文件无事务 ✗（部分提交窗口真实存在）**：
- `SaveChapter`：先写 `chapters/{id}.json` 再写 `project.json`（L254–270）——第二步失败残留"正文新/meta 旧"，无回滚；
- `CommitAnalysis`：先 `knowledge.json` 后 `project.json`（L388–402）；
- `ImportChapters`：多章节文件 → 清理失效章节 → knowledge → project（L135–175），失败残留面最大。

**现有自愈能力与边界**：分析链路靠"重析重写"近似幂等（重跑覆盖），但**草稿提交链路没有这种幂等**——提交日志协议确有必要。实现要点（据现状推导）：
1. 提交日志文件 append（intent + 变更内容，fsync）→ 标记 `prepared`；
2. 各文件**覆盖写**（覆盖写天然幂等，适合重放）→ 标记 `committed`；
3. 重启扫描未完成提交：重放至 committed（不"聪明回滚"，重放更简单可靠）；
4. 附带清理：崩溃会残留 `.tmp-*` 文件（writeJSONFile 的 defer 仅正常路径生效），恢复流程顺带清理。
