# 《详设.md》审查报告

> 审查对象：`D:/go/详设.md`（Agent 记忆系统详细设计 V1.0）
> 对照基准：novelagent 现有代码（store / analysis / agent / server / novel）+ `docs/features.md` 功能基线
> 日期：2026-10-22 ｜ 性质：仅审查指出，不改动原文

严重度：🔴 高（影响能否落地）｜🟡 中（流程/接口不闭环）｜🟢 低（完善项）

## 第一部分：整体设计思路、逻辑漏洞与遗漏模块

### P1 🔴 与已定大纲规划模块（F20–F23）的关系完全未定义
- **问题**：`docs/features.md` 已确认开发大纲模块（`outline.json` + `/api/outline` + 回灌续写），而详设的 `StoryPlan`（3.5，L230–267，含 global/volume/near_term 层级）覆盖了几乎相同的能力。1.2「不做清单」又写了"不一次性生成完整全书大纲"（L28），两份文档互相矛盾。若各做一套，会出现两套"计划/大纲"数据。
- **建议**（二选一，需拍板）：
  - **方案 A（推荐）**：StoryPlan 吸收大纲模块——`/api/outline` 的产出改为生成 `level=global/volume` 的 `StoryPlan(status=proposed)`，用户确认后转 `active`；F22 前端面板改为"计划视图"。只保留一套计划数据。
  - **方案 B**：明确分工并存——`outline.json` 是静态蓝图（给人看、导出用），StoryPlan 是可演进执行计划；并在两文档中写明同步规则（成本是双份数据）。

### P2 🔴 存量数据回填（backfill）流程缺失
- **问题**：详设只覆盖"提交草稿后增量提取"（5.1 输入是"最终草稿正文"）。对已导入的书（如《无边悔恨》19+ 章），记忆系统上线时是**空的**——检索不到事件/状态/伏笔，续写时记忆层形同虚设。没有回填，迭代 1–3 的验收都无从谈起。
- **建议**：新增"记忆初始化"设计节，两级策略：
  1. **低成本映射**：从现有 `knowledge.json` 直接映射初始记忆——`character.state` → `StoryState`（`review_required=true`）、`summaries` → 事件骨架（`confidence≤0.5`）、人物/世界观实体 → 实体注册表；
  2. **按需深度提取**：对近期 N 章跑完整 Extractor（阶段 A/B/C）。
  并在迭代 1 验收项中加入"存量书回填后，续写上下文能检索到初始状态记忆"。

### P3 🔴 章节版本号与记忆版本号在现有代码中不存在，但详设处处依赖
- **问题**：详设大量使用 `chapter_revision`（L284、L336、L562）与 `memory_revision`（L285、L412、L563），但现有 `novel.Chapter` 只有 `UpdatedAt` 没有 revision；`knowledge.json` 也没有全局记忆版本号（只有 `Project.Revision`）。文档 L765 最后承认"落地前需核实持久化方式"，但没有把这两项列为改造交付物。
- **建议**：在迭代 1 明确两个改造项：
  1. `Chapter` 增加 `revision int64`，`SaveChapter` 每次自增（与 `Project.Revision` 解耦或联动需写明）；
  2. 新增 `memory/meta.json` 持久化 `memory_revision`，规定递增时机（CommitAnalysis / FinishAnalysis / CommitService 均递增）。

### P4 🔴 实体注册与 ID 统一机制缺失（两套人物 ID 体系）
- **问题**：`StoryEvent.participants`、`StoryState.subject_id` 引用 `char_xxx`，六模块职责表里没有"实体注册/别名消解"的归属模块。现有 `knowledge.Characters` 已有自己的 ID（`c_xxx`）与别名合并逻辑（`merge.matchCharacter`）。若不打通，"人物存在性校验"（5.2 L394）与"按人物检索"（6.1）会在两套 ID 体系间断裂。
- **建议**：新增第 7 个逻辑模块 **Entity Registry**（实体注册表 `entities.json`）：职责=实体登记、别名归并（复用现有 matchCharacter 算法）、ID 分配；**记忆系统直接引用 knowledge 的实体 ID**，不另起一套。Extractor 只能"提议新人物"，注册表由 Validator 校验后由系统分配 ID。纳入迭代 1。

### P5 🔴 与后台分析流水线（analysis.Manager）的并发互斥未设计
- **问题**：现有 Manager 是常驻后台循环，会并发写 `knowledge.json` 与 `project.json`（`CommitAnalysis`）。详设的提交协议（4.3）只考虑了草稿侧版本校验，没有讨论"分析运行中用户确认草稿提交"的场景——两边同时推进 AnalyzedCount/Revision，可能互相触发版本失效或数据竞态。
- **建议**：明确互斥规则（推荐最简方案）：**提交前检查 `analysis.status`，若为 analyzing 则返回 409 引导稍后重试**；或将"提交"也接入 Manager 的 notify 循环串行执行。并在第十章异常表加一行"提交时分析运行中 → 拒绝并提示"。

### P6 🟡 缺少用户手动修正记忆的接口
- **问题**：模型提取错误是常态（错认人物状态、误判伏笔回收），但 8.2 接口表只有查询与 reconcile，**没有人工修正记忆实体的入口**。用户只能被动接受模型结果或整页重析。
- **建议**：新增 `PATCH /api/memory/{type}/{id}`（type ∈ event/state/thread/plan）：记录 `source="manual_edit"`、`record_version+1`、写变更历史；Validator 规则补充"manual_edit 的记录被自动提案覆盖时必须进入冲突清单，不允许静默覆盖"。

### P7 🟡 认知记录（Cognition）提出单独建模但未给数据结构
- **问题**：3.3（L191）说"建议单独建模为认知记录"，但全文没有给出它的字段结构；而状态属性表里"认知状态"又作为 StoryState 的一个类别存在。两者关系（替代还是并存）未定。
- **建议**：明确为独立记录类型并补结构：`{id, subject_id, content, known_since_event, status: known|wrong|forgotten, source_refs, record_version}`；StoryState 属性表中删除"认知状态"类别或注明由 Cognition 承接。

### P8 🟡 生成侧（续写 Orchestrator）提示词约束缺失
- **问题**：第十一章只有提取侧四类提示词（事件/状态/伏笔/计划），**没有"生成正文"的提示词约束**。现有 `agent.systemPrompt` 的规则（"知识摘要与正文冲突时服从正文"）在引入记忆层后必须同步修订，否则记忆段落注入后冲突规则不完整。
- **建议**：补一节"续写生成提示词约束"：① 注入段落的优先级次序与 6.1 一致（正文>状态>事件>伏笔>计划）；② 计划只作方向不写死逐章剧本；③ 人物只能使用其认知范围内信息（对接 T04）；④ 输出纯正文不含变更提案。并列出对现有 `systemPrompt` 的具体修改点。

## 第二部分：各部分之间的衔接与依赖关系

### P9 🟡 接口路径与现有后端风格、单作品现状不一致
- **问题**：8.2 全部用 `/api/works/:workId/...`，但现有代码是 `/api/chapters/{id}`（Go 1.22 `{}` 风格），且**当前是单作品架构**（无 work 概念，store 全局一份 project.json）。虽 L516 有"URL 应与现有风格保持一致"的提醒，但没有给出第一阶段的实际路径，work_id 的来源也未定义。
- **建议**：第一阶段明确：URL 采用 `/api/memory/...`、`/api/drafts/...`（与现有风格一致，无 workId 段）；`work_id` 字段保留在数据模型中但固定常量值（为多作品预留），并在文档中注明多作品属于后续迭代。

### P10 🟡 新 `POST /drafts` 与现有 `/api/continue` 的关系未定义
- **问题**：第九章整合表说"续写上下文组装：增加记忆检索结果"，意味着现有 `/api/continue`（F11–F15）继续存在；但 8.2 又新增 `POST /drafts` 作为续写入口。两条生成链路并存还是替代？没说。前端、测试都会受影响。
- **建议**：明确双轨并写进第九章：`/api/continue` 保留为**快速试写**（不建草稿、不入记忆、即生即弃）；`POST /drafts` 为**正式创作流**（草稿→检查→确认→入记忆）。前端以两个明确入口区分。或者决定第一阶段直接切换为 drafts 单轨、continue 下线——但要写明。

### P11 🟡 提交流程第 4 步语义模糊：重算变更集与用户确认的关系
- **问题**：4.3 第 4 步要求"从最终草稿内容生成或刷新 MemoryChangeSet"（L337），因为用户可能改过正文。但没说清：① 是自动重跑 Extractor 还是复用 recheck 结果？② 重算出的**新变更集**是否需要用户再次确认？若不确认就直接落库，违反 4.2"模型只能提议"的自己的原则。
- **建议**：明确为两段式：confirm 时若正文 hash 与最近一次通过检查的版本不一致 → 自动重跑阶段 A/B → 返回**刷新后的变更集摘要供用户展示确认**（第二次确认）→ 落库；可提供"自动接受无冲突变更集"的开关作为配置项。

### P12 🟡 草稿状态机缺转换表；多草稿并发未处理
- **问题**：8.1 只列了 6+1 个状态（L520–534），没有状态转换表：`editing` 从哪进、到哪出？`checking` 自动修订后回到哪？`needs_user_attention` 怎么退出？另外：两个草稿同时 `target_chapter_id=chapter_0021` 怎么办（生成时章节尚不存在，ID 预分配还是提交时分配）？
- **建议**：① 补状态转换表（当前态 × 事件 → 下一态），明确 pending_confirmation ⇄ editing → checking → pending_confirmation 回环，rejected/committed 为终态；② 第一阶段限制"同一目标章节同时只允许一个 pending 草稿"，并发冲突由既有 chapter_revision 校验兜底。

### P13 🟡 两处 ChangeSet 结构不一致；事件因果字段无结构化关联规范
- **问题**：4.1 的 `MemoryChangeSet`（L297–314）是按 `add_events/update_states/...` 分组的数组；5.3 的 change_set（L406–435）是 `operations[]`（op/target_id）扁平结构。同一事物两种形态，实现时必然二选一引发歧义。另外 `StoryEvent.consequences/preconditions`（L119–124）是纯文本数组，而 7.2 的依赖链修复恰恰需要事件间可追踪引用——文本无法支撑。
- **建议**：① 明确以 5.3 `operations[]` 形式为实现标准（每 op 携带 old/new 值与 evidence），4.1 的分组字段改为"operations 的分类视图"；② 规范 `preconditions/consequences` 元素结构：`{"event_id": "evt_xxx"}` 或 `{"text": "..."}` 至少其一，Validator 校验引用的 event_id 必须存在。

### P14 🟡 5.2 校验分类自相矛盾：世界观约束无法机械验证
- **问题**：5.2 表格把"状态合法性：状态变化不能违反明确的业务规则或世界观约束"（L394）列为业务规则校验，但 5.2 末尾（L401）自己强调"业务规则可以机械验证的，就不要依赖大模型自觉遵守"——"违反世界观约束"恰恰是语义问题，当前设计里也没有机读的世界观约束表示。
- **建议**：把该行拆成两条：a) **枚举与状态转换合法性**（纯机械，代码校验）；b) **世界观约束符合性**（语义，模型辅助判断 + 结果留痕 + 人工复核），与 L401 原则对齐。

## 第三部分：需要补充或完善的内容

### P15 🟢 source_refs 偏移语义未定义；编辑失效防护应从"建议"升级为硬性
- **问题**：`start_offset/end_offset`（L128–135）未定义按 rune 还是 byte——中文小说必须按 rune（与现有 `CountChars` 一致），否则证据定位错位。"建议同时保存章节版本号"（L135）在正文可编辑的系统里应该是硬性要求，不是建议。
- **建议**：明确 offset 单位=rune；`source_refs` 强制包含 `chapter_revision`，正文 revision 变化时相关证据自动标记失效（对接第七章）。

### P16 🟢 Retriever 无输入输出定义与第一阶段检索策略；上下文预算缺分配算法
- **问题**：六模块表里 Retriever 只有一句职责（L51），没有输入（从哪取关键词：用户指令？最近正文？）、输出（排序与截断规则）；6.1 只说"统一受 ContextChars 管理"（L459），没有 P0/P1/P2 的预算分配。T12 无法据此实现。
- **建议**：补 Retriever 规格——输入=`{最近正文末尾 N 字, 用户 direction, 激活计划}`；第一阶段策略=关键词倒排（人物名/别名/伏笔标题/事件摘要）+ LastSeen 排序 + 预算内截断（复用现有 `selectCharacters` 的打分思路即可起步）；预算分配给初始默认值（如 正文 60% / P0 记忆 20% / P1 15% / P2 5%，**标注为待实测调参的默认值**）。

### P17 🟢 依赖链示例缺伏笔环节；`needs_review` 未进通用字段
- **问题**：7.2 依赖链示例（L493–501）只有 事件→状态→计划，漏了伏笔（`thread.introduced_by_event/related_events` 本就是依赖关系，第 5 章改动同样会影响伏笔有效性）。7.2 用的 `needs_review` 标记（L506）没有出现在 3.1 通用字段表里。
- **建议**：依赖链补全为 事件→状态→**伏笔**→计划；3.1 通用字段表增加 `needs_review boolean`。

### P18 🟢 文档残留 UI 文案；验收清单与接口的补充
- **问题**：L720–722"重置勾选复制测试清单／勾选仅用于整理验收进度…"是网页 UI 文案残留，应删除。另缺：① 提交历史查询接口（第十章要求保留 commit 记录，但 8.2 无查询入口）；② 三个值得补的测试：T13 存量回填不产生重复事件（对接 P2）、T14 手动修正的记忆不被自动提案覆盖（对接 P6）、T15 记忆提取阶段的上下文预算限制（提取侧同样会撑爆，5.1 未约束）。
- **建议**：删除残留文案；8.2 增加 `GET /api/commits`；测试清单补 T13–T15。

## 审查结论

设计骨架（模型提议/程序校验/草稿隔离/可恢复提交）成立，四个迭代的切分也合理。**必须在开工前解决的是 P1–P5 五个红色项**，尤其是 P1（与大纲模块的关系）——它决定 features.md 基线是否要重写；P2（回填）决定记忆系统对存量书是否真的可用。黄色项建议随对应迭代的设计细化一并补齐；绿色项属文档修订，可在下一版详设中一次性处理。
