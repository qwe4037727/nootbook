## 阻塞发现

### F01 [P1] aborted 跳过恢复，但已成功写入的部分数据未撤销

位置：`internal/store/memory.go:162`，以及恢复时跳过 aborted 的分支（263、284 行）。

复现：先提交 revision 1 的空 events；令 states.json 目标写入失败，再提交同时更新 events/states 的 payload。events 按文件名排序先写成功，states 失败后日志被置 aborted。移除故障并重启，系统报告非安全态、revision 仍为 1，但 events 已是失败提交的数据。

影响：提交日志、版本和实际快照不一致，而且恢复流程认为健康。现有失败回归只覆盖首个目标就失败，没有覆盖部分文件已落盘。

验收要求：失败提交必须能够一致恢复或回滚，未收敛时不得继续暴露健康快照；补测多个目标中途失败及重启后的数据/日志/meta 一致性。

探针：`TestAcceptanceFollowupPartialPayloadAbort`，本机 FAIL。

### F02 [P1] committed 后 meta 写入失败，同进程重试仍能生成分叉

位置：`internal/store/memory.go:158` 的 committedMarked 错误分支，以及 113 行开始的提交入口基线判断。

复现：Windows 下持有 meta.json 读句柄，允许读取但阻止替换目标文件；提交成功写入 payload 和 committed 标记后，meta 原子替换失败。释放句柄后，同进程按旧基线 0 重试成功，形成两条非 aborted 的 0→1 记录。重启进入 `commit_chain_broken` 安全态。

影响：仅依赖重启修复 meta 不足以保障运行中的写入；正常重试可以制造不可接受的版本链。

验收要求：meta 对齐失败后，在下一次写入前恢复一致基线，或拒绝后续写入直至恢复；验证同进程重试和重启均不分叉。本探针在允许替换打开文件的平台会跳过，但本次 Windows 实测发生了目标故障并 FAIL，并非跳过。

探针：`TestAcceptanceFollowupMetaFailureRetry`，本机 FAIL。

### F03 [P1] 导入重置没有获取 memoryMu

位置：`internal/store/memory_init.go:445`；调用方 `internal/store/store.go:256`。

代码注释称持 store.mu 后获取 memoryMu，但调用方及 resetMemoryLocked 函数均没有实际获取 memoryMu。持有 store.mu 无法排斥只持 memoryMu 的记忆读写操作。

复现：主 goroutine 持有 memoryMu；另一 goroutine 按导入调用约定持 store.mu 后执行 resetMemoryLocked。重置仍然完成并重写记忆文件，证明没有等待记忆操作互斥锁。

影响：导入可与记忆提交交错清空 records/commits/meta，破坏新书隔离及提交一致性。当前探针证明缺少互斥，未宣称已穷尽每种交错的数据结果。

验收要求：重置与记忆读写应受一致的互斥协议保护，并检查锁顺序及并发导入/提交不会混入旧数据。

探针：`TestAcceptanceFollowupResetAcquiresMemoryLock`，本机 FAIL。
