## 3. 阻塞问题及影响

### A01 / P1：初始化期间重启后永久误判为正在运行

- 来源：V1.2 §9.4.5 要求 mapping 中断后按 origin 查重续跑；§9.3 的 409 前提是“相同任务仍在执行”。
- 位置：[memory_init.go](../internal/store/memory_init.go#L155)、[store.New](../internal/store/store.go#L125)。启动只恢复提交日志，没有恢复/清理初始化任务状态。
- 复现：将测试存储停留在持久化 `mapping`，重新 `New(dir)`，再调用 `InitializeMemory()`。
- 实际：新进程没有 mapping worker，却返回 `store: memory initialization already running`；后续 POST 会一直 409，不能自行续跑。
- 影响：一次正常进程中断就可能让初始化永久不可用；不能把“prepared 文件重放成功”视为初始化完整恢复。
- 验收要求：启动恢复应区分存活任务与遗留状态，恢复或允许安全重试；重启后经公开初始化入口达到终态，且不重复写记录/加版本。
- 证据：`TestAcceptanceReviewInterruptedInitialization`，见 [故障输出](acceptance-evidence/20261022/fault-probes.txt)。

### A02 / P1：提交写入失败后允许新提交，生成不可恢复分叉

- 来源：V1.2 §11 的连续提交链、单次递增、可重放恢复不变量；原始详设 §10 的失败重试要求。
- 位置：[memory.go](../internal/store/memory.go#L140)。prepared 已持久化而 apply 失败时直接返回，既不在后续写入前恢复，也不阻止第二个同基线提交。
- 复现：以临时目录阻塞 `events.json` 写入，使首个提交失败；移走故障目录后，以当前基线 0 重试一次提交，再重新打开存储。
- 实际：重试报告成功，但日志保留两条 `basedOn=0,target=1`；重启进入 `commit_chain_broken` 安全态。
- 影响：可重试的磁盘错误被扩大成永久记忆写入失败；对“重试成功”的返回不可信，初始化与 reconcile 均受底层机制影响。
- 验收要求：有未完成提交时先完成恢复或拒绝新写；不得追加同基线分叉；覆盖 payload、committed、meta 各写入失败点后重试与重启。
- 证据：`TestAcceptanceReviewRetryAfterPayloadWriteFailure`，同一 [故障输出](acceptance-evidence/20261022/fault-probes.txt)。

### A03 / P1：恢复校验未验证单条日志的递增与状态合法性

- 来源：V1.2 §8.3 `target=basedOn+1`、§11.1 只有 prepared/committed，以及 R7 损坏日志应进安全态。
- 位置：[memory.go](../internal/store/memory.go#L204)。当前只检查相邻 basedOn/target 和 target 重复，不完整验证每条记录。
- 复现及实际：`basedOn=0,target=9,status=committed` 被当作合法链，meta 被推进到 9，safeState=false；`status=invalid_status` 也未进入安全态，记录被略过。
- 影响：可解析 JSON 的非法日志能伪装正常恢复，破坏“一次提交恰好 +1”和损坏保护。原 U32 只构造跨记录断链，未覆盖这类损坏。
- 验收要求：恢复重放前验证 target、status、ID 唯一性、类型及载荷边界；非法记录不能修改目标文件/meta，应可诊断地拒绝写入。
- 证据：`TestAcceptanceReviewMalformedCommitRecords/revision_jump` 和 `/unknown_status`，见 [故障输出](acceptance-evidence/20261022/fault-probes.txt)。

### A04 / P1：导入替换整书后保留旧记忆和 ready 状态

- 来源：原始详设 §3“作品为数据隔离单位”、§9 章节/记忆衔接；F1 明确导入替换当前全部章节。单作品不等于允许不同导入作品共享剧情事实。
- 位置：[ImportChapters](../internal/store/store.go#L180)、[ready 短路](../internal/store/memory_init.go#L153)、[顺序回调](../internal/store/memory_init.go#L423)。导入清空旧知识库，但旧 states 与 init_state 保留；回调只处理 events。
- 复现：书 A 有 Alice=injured，完成初始化；导入书 B（Bob=healthy）替换全部章节，读取记忆概览。
- 实际：仍为 ready，旧事件/状态数量保留（测试为 events=1、states=1）；旧事件被标 chapter_deleted，但旧状态没有失效处理；再次 initialize 仍走 ready 幂等短路。
- 影响：新书不能通过正常初始化入口建立自身记忆，记忆概览与当前作品不一致。当前续写尚未读取 memory 文件，因此不宣称本测试证明旧记忆已污染实际续写。
- 验收要求：定义替换整书的记忆归档/重置/失效策略，保护旧数据且明确提示；新书可重新初始化，旧状态不可被当作当前书状态。必须通过公开导入/查询/初始化流程验证。
- 证据：`TestAcceptanceReviewReplacingBookDoesNotKeepReadyMemory`，见 [故障输出](acceptance-evidence/20261022/fault-probes.txt)。

### D01 / P2：现有验收材料将部分契约与未交付入口写成“全部闭环”

`acceptance.md` 的 U9 引用 `CheckSourceRefAgainstContent`，但该函数只接收正文字符串和 ref，不接收当前章节 revision，也不写 needsReview；测试也未断言 evidence_stale。U22 只测试拒绝同作用域双 active，不测试“自动替代旧计划”；U33 未覆盖 expectedRecordVersion。它们只能证明辅助契约，不能证明完整行为。应保留历史报告，但正式发布说明以本报告限定范围为准。

### D02 / P2：范围与接口规格仍有待收敛之处

V1.2 §11/§12 标题仍称“本期不实现”，而 #4/#8 已实现；issues #1 记载“待 yj 追认”。原始 §13/末尾第一阶段范围也不一致。§9.3 写明全量重初始化 400 `reinit_not_supported`，但 §12.3 未定义识别这类请求的参数，handler 不解码请求体，没有该错误分支。当前不能把该 400 契约列为通过；应明确接口格式和交付边界后复测，不能自行发明参数算作验收。
